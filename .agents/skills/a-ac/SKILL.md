## 检查清单目的："需求编写的单元测试"

**核心概念**：检查清单是**需求编写的单元测试**——它们在给定领域内验证需求的质量、清晰度和完整性。

**不是用于验证/测试**：

- ❌ 不是"验证按钮点击正确"
- ❌ 不是"测试错误处理正常工作"
- ❌ 不是"确认 API 返回 200"
- ❌ 不是检查代码/实现是否匹配 spec

**而是用于需求质量验证**：

- ✅ "是否定义了所有卡片类型的视觉层级需求？"（完整性）
- ✅ "'突出显示'是否用量化的大小/位置来定义？"（清晰性）
- ✅ "所有交互元素的悬停状态需求是否一致？"（一致性）
- ✅ "是否定义了键盘导航的无障碍需求？"（覆盖范围）
- ✅ "spec 是否定义了 logo 图片加载失败时的处理？"（边界情况）

**比喻**：如果你的 spec 是用英文编写的代码，检查清单就是它的单元测试套件。你在测试需求是否编写良好、完整、无歧义且准备好实施——而不是测试实现是否正常。

## 用户输入

```text
$ARGUMENTS
```

你**必须**在继续之前考虑用户输入（如果非空）。

## 前置检查

**检查扩展钩子（生成检查清单前）**：
- 检查项目根目录下是否存在 `.specify/extensions.yml`
- 如果存在，读取它并查找 `hooks.before_checklist` 键下的条目
- 如果 YAML 无法解析或无效，静默跳过钩子检查并正常继续
- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或为 null/空，则视该钩子为可执行
  - 如果钩子定义了非空的 `condition`，跳过该钩子，将条件评估留给 HookExecutor 实现
- 从钩子命令名构造斜杠命令时，将点号（`.`）替换为连字符（`-`）。例如 `speckit.git.commit` → `/speckit-git-commit`
- 对于每个可执行的钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：
    ```
    ## 扩展钩子

    **可选前置钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    执行：`/{command}`
    ```
  - **强制钩子**（`optional: false`）：
    ```
    ## 扩展钩子

    **自动前置钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND：{command}

    在继续到执行步骤之前等待钩子命令的结果。
    ```
- 如果没有注册任何钩子或 `.specify/extensions.yml` 不存在，则静默跳过

## 执行步骤

1. **设置**：从仓库根目录运行 `.specify/scripts/bash/check-prerequisites.sh --json`，解析 JSON 获取 FEATURE_DIR 和 AVAILABLE_DOCS 列表。
   - 所有文件路径必须是绝对路径。
   - 对于参数中的单引号（如 "I'm Groot"），使用转义语法：例如 'I'\''m Groot'（或尽可能使用双引号："I'm Groot"）。

2. **如果存在**：加载 `.specify/memory/constitution.md` 了解项目原则和治理约束。

3. **明确意图（动态）**：推导出最多三个初始上下文澄清问题（非预置目录）。它们必须：
   - 从用户的表述 + 从 spec/plan/tasks 提取的信号生成
   - 只询问会实质改变检查清单内容的信息
   - 如果已在 `$ARGUMENTS` 中明确，则单独跳过
   - 优先精确而非广度

   生成算法：
   1. 提取信号：功能领域关键词（如 auth、latency、UX、API）、风险指标（"critical"、"must"、"compliance"）、干系人提示（"QA"、"review"、"security team"）和显式交付物（"a11y"、"rollback"、"contracts"）。
   2. 将信号聚类为候选关注领域（最多 4 个），按相关性排序。
   3. 如果未明确说明，识别可能的受众和时机（作者、审查者、QA、发布）。
   4. 检测缺失的维度：范围广度、深度/严谨度、风险重点、排除边界、可衡量的验收标准。
   5. 从这些原型中选择问题：
      - 范围细化（例如"是否应包含 X 和 Y 的集成接触点，还是仅限于局部模块的正确性？"）
      - 风险优先级（例如"哪些潜在风险区域应进行强制关卡检查？"）
      - 深度校准（例如"这是轻量级的提交前检查清单还是正式的发布关卡？"）
      - 受众定位（例如"这将由作者自己使用还是在 PR 审查时由同事使用？"）
      - 边界排除（例如"本次是否应显式排除性能调优项？"）
      - 场景类缺失（例如"未检测到恢复流程——回滚/部分失败路径是否在范围内？"）

   问题格式化规则：
   - 如果提供选项，生成一个简洁的表格，列名为：选项 | 候选 | 为什么重要
   - 最多 A–E 选项；如果自由格式答案更清晰则省略表格
   - 绝不要求用户重复他们已经说过的话
   - 避免推测性类别（不幻觉）。如果不确定，明确询问："请确认 X 是否在范围内。"

   无法交互时的默认值：
   - 深度：标准
   - 受众：审查者（PR）如果与代码相关；否则为作者
   - 关注点：前 2 个相关性聚类

   输出问题（标记 Q1/Q2/Q3）。回答后：如果仍有 ≥2 个场景类（备选/异常/恢复/非功能领域）不明确，你可以询问最多两个更有针对性的追问（Q4/Q5），每个附带一行理由（例如"未解决的恢复路径风险"）。不要超过五个问题。如果用户明确拒绝更多，跳过追问。

4. **理解用户请求**：结合 `$ARGUMENTS` + 澄清答案：
   - 推导检查清单主题（例如安全、审查、部署、UX）
   - 整合用户提到的显式必备项
   - 将关注选择映射到分类框架
   - 从 spec/plan/tasks 推断任何缺失的上下文（不进行幻觉）

5. **加载功能上下文**：从 FEATURE_DIR 读取：
   - spec.md：功能需求和范围
   - plan.md（如果存在）：技术细节、依赖关系
   - tasks.md（如果存在）：实施任务

   **上下文加载策略**：
   - 只加载与当前关注领域相关的必要部分（避免全文件转储）
   - 优先将长章节归纳为简洁的场景/需求要点
   - 使用渐进式披露：仅当检测到缺口时才进行后续检索
   - 如果源文档很大，生成中间摘要项而非嵌入原始文本

6. **生成检查清单**——创建"需求的单元测试"：
   - 如果 `FEATURE_DIR/checklists/` 目录不存在则创建
   - 生成唯一的检查清单文件名：
     - 使用基于领域的简短描述性名称（例如 `ux.md`、`api.md`、`security.md`）
     - 格式：`[领域].md`
   - 文件处理行为：
     - 如果文件**不存在**：创建新文件，从 CHK001 开始编号
     - 如果文件**存在**：追加新项到现有文件，从最后一个 CHK ID 继续（例如如果最后一个项是 CHK015，新项从 CHK016 开始）
   - 绝不删除或替换现有检查清单内容——始终保留并追加

   **核心原则——测试需求本身，而非实现**：
   每个检查清单项必须评估**需求本身**的以下方面：
   - **完整性**：所有必要的需求是否都存在？
   - **清晰性**：需求是否无歧义且具体？
   - **一致性**：需求之间是否相互一致？
   - **可衡量性**：需求是否能客观验证？
   - **覆盖范围**：是否处理了所有场景/边界情况？

   **分类结构**——按需求质量维度分组：
   - **需求完整性**（所有必要的需求是否都已文档化？）
   - **需求清晰性**（需求是否具体且无歧义？）
   - **需求一致性**（需求之间是否一致且无冲突？）
   - **验收标准质量**（成功标准是否可衡量？）
   - **场景覆盖**（是否处理了所有流程/情况？）
   - **边界情况覆盖**（是否定义了边界条件？）
   - **非功能需求**（性能、安全、无障碍等——是否明确定义？）
   - **依赖与假设**（是否已文档化并验证？）
   - **歧义与冲突**（哪些需要澄清？）

   **如何编写检查清单项——"需求的单元测试"**：

   ❌ **错误**（测试实现）：
   - "验证首页显示 3 个剧集卡片"
   - "测试桌面端悬停状态工作正常"
   - "确认 logo 点击导航到首页"

   ✅ **正确**（测试需求质量）：
   - "是否指定了精选剧集的具体数量和布局？"[完整性]
   - "'突出显示'是否用量化的大小/位置来定义？"[清晰性]
   - "所有交互元素的悬停状态需求是否一致？"[一致性]
   - "是否为所有交互式 UI 定义了键盘导航需求？"[覆盖范围]
   - "logo 图片加载失败时的降级行为是否已指定？"[边界情况]
   - "是否为异步剧集数据定义了加载状态？"[完整性]
   - "spec 是否定义了竞争 UI 元素的视觉层级？"[清晰性]

   **项结构**：
   每个项应遵循以下模式：
   - 以问题形式询问需求质量
   - 关注 spec/plan 中**已编写**（或未编写）的内容
   - 在方括号中包含质量维度 [完整性/清晰性/一致性/等]
   - 检查现有需求时引用 spec 章节 `[Spec §X.Y]`
   - 检查缺失需求时使用 `[缺口]` 标记

   **按质量维度示例**：

   完整性：
   - "是否为所有 API 失败模式定义了错误处理需求？[缺口]"
   - "是否为所有交互元素指定了无障碍需求？[完整性]"
   - "是否为响应式布局定义了移动端断点需求？[缺口]"

   清晰性：
   - "'快速加载'是否用量化的时间阈值来定义？[清晰性, Spec §NFR-2]"
   - "'相关剧集'的选择标准是否明确定义？[清晰性, Spec §FR-5]"
   - "'突出'是否定义了可衡量的视觉属性？[歧义, Spec §FR-4]"

   一致性：
   - "导航需求是否在所有页面间保持一致？[一致性, Spec §FR-10]"
   - "卡片组件的需求在首页和详情页之间是否一致？[一致性]"

   覆盖范围：
   - "是否定义了零状态场景（无剧集）的需求？[覆盖范围, 边界情况]"
   - "是否处理了并发用户交互场景？[覆盖范围, 缺口]"
   - "是否指定了部分数据加载失败的需求？[覆盖范围, 异常流程]"

   可衡量性：
   - "视觉层级需求是否可衡量/可测试？[验收标准, Spec §FR-1]"
   - "'均衡的视觉权重'能否被客观验证？[可衡量性, Spec §FR-2]"

   **场景分类与覆盖**（关注需求质量）：
   - 检查需求是否涵盖：主流程、备选流程、异常/错误、恢复、非功能场景
   - 对每个场景类别，询问："[场景类型] 的需求是否完整、清晰且一致？"
   - 如果场景类缺失："[场景类型] 的需求是故意排除的还是遗漏了？[缺口]"
   - 当存在状态变更时，包含恢复/回滚："是否为迁移失败定义了回滚需求？[缺口]"

   **可追溯性要求**：
   - **最低要求**：≥80% 的项必须包含至少一个可追溯性引用
   - 每个项应引用：spec 章节 `[Spec §X.Y]`，或使用标记：`[缺口]`、`[歧义]`、`[冲突]`、`[假设]`
   - 如果不存在 ID 系统："是否建立了需求和验收标准 ID 方案？[可追溯性]"

   **发现并解决问题**（需求质量的问题）：
   对需求本身提问：
   - 歧义："术语 '快速' 是否用具体指标量化？[歧义, Spec §NFR-1]"
   - 冲突："§FR-10 和 §FR-10a 之间的导航需求是否冲突？[冲突]"
   - 假设："'始终可用的播客 API' 的假设是否经过验证？[假设]"
   - 依赖："外部播客 API 的需求是否已文档化？[依赖, 缺口]"
   - 缺少定义："'视觉层级' 是否定义了可衡量的标准？[缺口]"

   **内容整合**：
   - 软上限：如果原始候选项超过 40 个，按风险/影响进行优先级排序
   - 合并检查同一需求方面的近似重复项
   - 如果有超过 5 个低影响的边界情况，创建一个项："边界情况 X、Y、Z 是否在需求中处理？[覆盖范围]"

   **🚫 绝对禁止**——这些会使它成为实现测试而非需求测试：
   - ❌ 任何以"验证"、"测试"、"确认"、"检查"开头 + 实现行为的项
   - ❌ 引用代码执行、用户操作、系统行为
   - ❌ "正确显示"、"正常工作"、"如预期运行"
   - ❌ "点击"、"导航"、"渲染"、"加载"、"执行"
   - ❌ 测试用例、测试计划、QA 流程
   - ❌ 实现细节（框架、API、算法）

   **✅ 必需的模式**——这些测试需求质量：
   - ✅ "[需求类型] 是否为 [场景] 定义/指定/记录了？"
   - ✅ "[模糊术语] 是否用量化标准/具体标准来量化/澄清？"
   - ✅ "[章节 A] 和 [章节 B] 之间的需求是否一致？"
   - ✅ "[需求] 能否被客观衡量/验证？"
   - ✅ "[边界情况/场景] 是否在需求中处理？"
   - ✅ "spec 是否定义了 [缺失方面]？"

7. **结构参考**：按照 `.specify/templates/checklist-template.md` 中的规范模板生成检查清单，包括标题、元信息段、类别标题和 ID 格式。如果模板不可用，使用：H1 标题、目的/创建元信息行、`##` 类别章节，包含 `- [ ] CHK### <需求项>` 行，ID 从 CHK001 开始全局递增。

8. **报告**：输出检查清单文件的完整路径、项数，并总结本次运行是创建了新文件还是追加到现有文件。总结：
   - 选择的关注领域
   - 深度级别
   - 参与者/时机
   - 用户指定的任何显式必备项是否已纳入

**重要**：每次 `/a-ac` 命令调用使用一个简短、描述性的检查清单文件名，要么创建新文件，要么追加到现有文件。这允许：

- 多种类型的检查清单（例如 `ux.md`、`test.md`、`security.md`）
- 简单、易记的文件名，表明检查清单的目的
- 在 `checklists/` 文件夹中易于识别和导航

为避免混乱，使用描述性类型，并在完成后清理过时的检查清单。

## 检查清单类型及示例项

**UX 需求质量：** `ux.md`

示例项（测试需求，而非实现）：

- "视觉层级需求是否用可衡量标准定义？[清晰性, Spec §FR-1]"
- "UI 元素的数量和位置是否明确指定？[完整性, Spec §FR-1]"
- "交互状态需求（悬停、聚焦、激活）是否一致定义？[一致性]"
- "是否为所有交互元素指定了无障碍需求？[覆盖范围, 缺口]"
- "图片加载失败时的降级行为是否定义？[边界情况, 缺口]"
- "'突出显示'能否被客观衡量？[可衡量性, Spec §FR-4]"

**API 需求质量：** `api.md`

示例项：

- "是否为所有失败场景指定了错误响应格式？[完整性]"
- "频率限制需求是否用量化阈值来定义？[清晰性]"
- "所有端点的认证需求是否一致？[一致性]"
- "是否为外部依赖定义了重试/超时需求？[覆盖范围, 缺口]"
- "版本策略是否在需求中记录？[缺口]"

**性能需求质量：** `performance.md`

示例项：

- "性能需求是否用具体指标量化？[清晰性]"
- "是否定义了所有关键用户旅程的性能目标？[覆盖范围]"
- "不同负载条件下的性能需求是否已指定？[完整性]"
- "性能需求能否被客观衡量？[可衡量性]"
- "高负载场景下的降级需求是否定义？[边界情况, 缺口]"

**安全需求质量：** `security.md`

示例项：

- "是否为所有受保护资源指定了认证需求？[覆盖范围]"
- "是否为敏感信息定义了数据保护需求？[完整性]"
- "威胁模型是否已文档化且需求与之对齐？[可追溯性]"
- "安全需求是否与合规义务一致？[一致性]"
- "安全故障/数据泄露响应需求是否定义？[缺口, 异常流程]"

## 反例：不该做什么

**❌ 错误——这些测试实现，而非需求：**

```markdown
- [ ] CHK001 - 验证首页显示 3 个剧集卡片 [Spec §FR-001]
- [ ] CHK002 - 测试桌面端悬停状态正确工作 [Spec §FR-003]
- [ ] CHK003 - 确认 logo 点击导航到首页 [Spec §FR-010]
- [ ] CHK004 - 检查相关剧集部分显示 3-5 个项目 [Spec §FR-005]
```

**检查扩展钩子（生成检查清单后）**：
检查项目根目录下是否存在 `.specify/extensions.yml`。
- 如果存在，读取它并查找 `hooks.after_checklist` 键下的条目

- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用

