## 前置检查

**检查扩展钩子（定义规格前）**：
- 检查项目根目录下是否存在 `.specify/extensions.yml`
- 如果存在，读取它并查找 `hooks.before_specify` 键下的条目
- 如果 YAML 无法解析或无效，静默跳过钩子检查并正常继续
- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或为 null/空，则视该钩子为可执行
  - 如果钩子定义了非空的 `condition`，跳过该钩子，将条件评估留给 HookExecutor 实现
- 从钩子命令名构造斜杠命令时，将点号（`.`）替换为连字符（`-`）。例如 `speckit.git.commit` → `/speckit-git-commit`
- 对于每个可执行的钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：
    ```
    ## 扩展钩子

    **可选前置钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    执行：`/{command}`
    ```
  - **强制钩子**（`optional: false`）：
    ```
    ## 扩展钩子

    **自动前置钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND：{command}

    在继续到大纲之前等待钩子命令的结果。
    ```
- 如果没有注册任何钩子或 `.specify/extensions.yml` 不存在，则静默跳过

## 大纲

触发消息中 `/a-spec` 后的文本**就是**功能描述。假设它始终在当前对话中可用，即使下方的 `$ARGUMENTS` 看起来是字面值。除非用户提供的命令为空，否则不要要求用户重复。

根据功能描述执行以下步骤：

1. **生成简洁的短名称**（2-4 个词）：
   - 分析功能描述并提取最有意义的关键词
   - 创建一个 2-4 个词的短名称，捕捉功能的本质
   - 尽可能使用 动作-名词 格式（例如 "add-user-auth"、"fix-payment-bug"）
   - 保留技术术语和缩写（OAuth2、API、JWT 等）
   - 保持简洁但足够的描述性，让人一目了然
   - 示例：
     - "I want to add user authentication" → "user-auth"
     - "Implement OAuth2 integration for the API" → "oauth2-api-integration"
     - "Create a dashboard for analytics" → "analytics-dashboard"
     - "Fix payment processing timeout bug" → "fix-payment-timeout"

2. **分支创建**（可选，通过钩子）：

   如果前置检查中的 `before_specify` 钩子成功执行，它将创建/切换到一个 git 分支并输出包含 `BRANCH_NAME` 和 `FEATURE_NUM` 的 JSON。记录这些值供参考，但分支名称**不决定** spec 目录名称。

   如果用户明确提供了 `GIT_BRANCH_NAME`，将其传递给钩子，使分支脚本使用该确切值作为分支名称（绕过所有前缀/后缀的生成）。

3. **创建 spec 功能目录**：

   除非用户明确提供 `SPECIFY_FEATURE_DIRECTORY`，否则 specs 默认存放在 `docs/00-7待办/` 对应分层（`01-前端`、`02-backend`、`03-core-backend`、`04-混合`）目录下。

   **`SPECIFY_FEATURE_DIRECTORY` 的解析顺序**：
   1. 如果用户明确提供了 `SPECIFY_FEATURE_DIRECTORY`（例如通过环境变量、参数或配置），直接使用
   2. 否则，自动在 `docs/00-7待办/<对应分层>/` 下生成：
      - 检查 `.specify/init-options.json` 中的 `feature_numbering`（首选）或 `branch_numbering`（已弃用，仅迁移用——将在未来版本中移除）
      - 如果是 `"timestamp"`：前缀为 `YYYYMMDD-HHMMSS`（当前时间戳）
      - 如果是 `"sequential"` 或未设置：前缀为 `NNN`（扫描 `docs/00-7待办/` 各分层与 `已完成/` 中现有目录后的下一个可用三位数）
      - 构造目录名：`<前缀>-<短名称>`（例如 `132-user-auth`）
      - 设置 `SPECIFY_FEATURE_DIRECTORY` 为 `docs/00-7待办/<对应分层>/<目录名>`（未指定分层时默认归入 `04-混合/`）
      - 如果使用了 `branch_numbering`（且 `feature_numbering` 不存在），输出一行警告："⚠️ init-options.json 中的 `branch_numbering` 已弃用。请重命名为 `feature_numbering`。"

   **创建目录和 spec 文件**：
   - `mkdir -p SPECIFY_FEATURE_DIRECTORY`
   - 通过 Spec Kit 预设/模板解析栈解析当前激活的 `spec-template`
   - 将解析后的 `spec-template` 文件复制到 `SPECIFY_FEATURE_DIRECTORY/spec.md` 作为起点
   - 设置 `SPEC_FILE` 为 `SPECIFY_FEATURE_DIRECTORY/spec.md`
   - 将解析后的路径持久化到 `.specify/feature.json`：
     ```json
     {
       "feature_directory": "<解析后的功能目录>"
     }
     ```
     写入实际的解析后目录路径值（例如 `docs/00-7待办/04-混合/003-user-auth` 或子仓待办路径），而不是字面字符串 `SPECIFY_FEATURE_DIRECTORY`。
     这允许下游命令（`/a-plan`、`/a-tasks` 等）定位功能目录而无需依赖 git 分支命名约定。

   **重要说明**：
   - 每次 `/a-spec` 调用只能创建一个功能
   - spec 目录名和 git 分支名是独立的——它们可以相同，但这取决于用户的选择
   - spec 目录和文件始终由此命令创建，而不是由钩子创建

4. 加载解析后的激活 `spec-template` 文件，了解所需的章节结构。

5. **如果存在**：加载 `.specify/memory/constitution.md` 了解项目原则和治理约束。

6. 按照以下执行流程：
   1. 从参数中解析用户描述
      如果为空：报错 "未提供功能描述"
   2. 从描述中提取关键概念
      识别：参与者、操作、数据、约束
   3. 对于不明确的方面：
      - 基于上下文和行业标准做出合理的推断
      - 仅当以下情况时才标记 [NEEDS CLARIFICATION：具体问题]：
        - 该选择会显著影响功能范围或用户体验
        - 存在多种合理的解释且结果不同
        - 没有合理的默认值
      - **限制：总共最多 3 个 [NEEDS CLARIFICATION] 标记**
      - 按影响程度优先排序待澄清项：范围 > 安全/隐私 > 用户体验 > 技术细节
   4. 填写用户场景与测试章节
       如果没有清晰的用户流程：报错 "无法确定用户场景"
       用户场景中的"验收场景"必须包含具体的 Given-When-Then 格式，作为后续测试生成的直接依据。每个用户故事至少包含一个正常路径和一个异常路径的验收场景。
   5. 生成功能需求
      每个需求必须可测试
      对未指定的细节使用合理的默认值（在假设章节中记录）
   6. 定义成功标准
      创建可衡量的、与技术无关的结果
      包括定量指标（时间、性能、数量）和定性指标（用户满意度、任务完成度）
      每个标准必须无需实现细节即可验证
   7. 识别关键实体（如果涉及数据）
   8. 返回：成功（spec 已准备好进行规划）

7. 使用模板结构将 spec 写入 SPEC_FILE，用从功能描述（参数）中推导的具体细节替换占位符，同时保留章节顺序和标题。

8. **规格质量校验**：在写入初始 spec 后，根据质量标准进行校验：

   a. **创建 Spec 质量检查清单**：在 `SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md` 生成包含以下验证项的检查清单文件：

      ```markdown
      # 规格质量检查清单：[功能名称]

      **目的**：在进入规划前验证规格的完整性和质量
      **创建时间**：[日期]
      **功能**：[链接到 spec.md]

      ## 内容质量

      - [ ] 不包含实现细节（语言、框架、API）
      - [ ] 关注用户价值和业务需求
      - [ ] 面向非技术干系人编写
      - [ ] 所有必填章节已完成

      ## 需求完整性

      - [ ] 没有残留的 [NEEDS CLARIFICATION] 标记
      - [ ] 需求可测试且无歧义
      - [ ] 成功标准是可衡量的
      - [ ] 成功标准与技术无关（不包含实现细节）
      - [ ] 所有验收场景已定义
      - [ ] 边界情况已识别
      - [ ] 范围已明确界定
      - [ ] 依赖关系和假设已识别

      ## 功能就绪度

      - [ ] 所有功能需求都有明确的验收标准
      - [ ] 用户场景覆盖主要流程
      - [ ] 功能满足成功标准中定义的可衡量结果
      - [ ] 规格中不泄露实现细节

      ## 备注

      - 标记为不完整的项目需要在 `/speckit-clarify` 或 `/a-plan` 前更新 spec
      ```

   b. **运行验证检查**：对照检查清单的每一项审查 spec：
      - 对于每一项，判断是否通过
      - 记录具体发现的问题（引用相关 spec 章节）

   c. **处理验证结果**：

      - **如果所有项都通过**：标记检查清单为完成，继续到强制后置执行钩子章节

      - **如果有项未通过（不包括 [NEEDS CLARIFICATION]）**：
        1. 列出未通过的项和具体问题
        2. 更新 spec 解决每个问题
        3. 重新运行验证直到所有项通过（最多 3 轮）
        4. 如果 3 轮后仍未通过，在检查清单备注中记录剩余问题并警告用户

      - **如果仍有 [NEEDS CLARIFICATION] 标记**：
        1. 从 spec 中提取所有 [NEEDS CLARIFICATION：...] 标记
        2. **限制检查**：如果超过 3 个标记，只保留最重要的 3 个（按范围/安全/用户体验影响），其余的做出合理推断
        3. 对于每个需要澄清的项（最多 3 个），按以下格式向用户展示选项：

           ```markdown
           ## 问题 [N]：[主题]

           **上下文**：[引用相关 spec 章节]

           **我们需要了解**：[来自 NEEDS CLARIFICATION 标记的具体问题]

           **建议答案**：

           | 选项 | 答案 | 影响 |
           |------|------|------|
           | A    | [建议答案 1] | [对功能的影响] |
           | B    | [建议答案 2] | [对功能的影响] |
           | C    | [建议答案 3] | [对功能的影响] |
           | 自定义 | 提供你自己的答案 | [说明如何提供自定义输入] |

           **你的选择**：_[等待用户响应]_
           ```

        4. **关键——表格格式**：确保 markdown 表格格式正确：
           - 使用一致的间距，管道符对齐
           - 每个单元格应包含内容两边留空格：`| 内容 |`
           - 标题分隔符必须至少有 3 个短横：`|------|`
           - 测试表格在 markdown 预览中是否正确渲染
        5. 顺序编号问题（Q1、Q2、Q3——最多 3 个）
        6. 在等待回复前将所有问题一起展示
        7. 等待用户回复所有问题的选择（例如 "Q1：A, Q2：自定义 - [详情], Q3：B"）
        8. 用用户选择或提供的答案替换每个 [NEEDS CLARIFICATION] 标记来更新 spec
        9. 所有澄清完成后重新运行验证

   d. **更新检查清单**：每次验证迭代后，用当前的通过/失败状态更新检查清单文件

## 快速指南

- 关注用户需要的**是什么**和**为什么**
- 避免如何实现（不涉及具体技术细节）
- 面向业务干系人编写，而非开发人员
- 不要在 spec 中嵌入任何检查清单。那将是单独的命令

### 章节要求

- **必填章节**：每个功能都必须完成
- **可选章节**：仅当与功能相关时包含
- 如果某个章节不适用，直接删除（不要留 "N/A"）

### AI 生成指南

当根据用户提示创建 spec 时：

1. **做出合理推断**：使用上下文、行业标准和常见模式来填补空白
2. **记录假设**：在假设章节中记录合理的默认值
3. **限制澄清项**：最多 3 个 [NEEDS CLARIFICATION] 标记——仅用于以下关键决策：
   - 会显著影响功能范围或用户体验
   - 有多种合理解释且结果不同
   - 缺乏任何合理的默认值
4. **优先排序待澄清项**：范围 > 安全/隐私 > 用户体验 > 技术细节
5. **像测试人员一样思考**：每个模糊的需求都应无法通过"可测试且无歧义"的检查项
6. **常见的需要澄清的领域**（仅当没有合理的默认值时）：
   - 功能范围和边界（包含/排除特定用例）
   - 用户类型和权限（如果可能有多种相互冲突的解释）
   - 安全/合规要求（当涉及法律/财务重要性时）

**合理默认值的示例**（无需询问这些）：

- 数据保留：该领域的行业标准实践
- 性能目标：标准的 Web/移动应用预期，除非另有指定
- 错误处理：用户友好的消息配合适当的降级方案
- 认证方式：Web 应用的标准会话或 OAuth2
- 集成模式：使用项目合适的模式（Web 服务用 REST/GraphQL，库用函数调用，工具用 CLI 参数等）

### 成功标准指南

成功标准必须：

1. **可衡量**：包含具体的指标（时间、百分比、数量、速率）
2. **技术无关**：不提及框架、语言、数据库或工具
3. **以用户为中心**：从用户/业务角度描述结果，而非系统内部实现
4. **可验证**：无需了解实现细节即可测试/验证

**好示例**：

- "用户可在 3 分钟内完成结账"
- "系统支持 10,000 并发用户"
- "95% 的搜索在 1 秒内返回结果"
- "任务完成率提升 40%"

**坏示例**（关注实现）：

- "API 响应时间低于 200ms"（过于技术化，应使用"用户瞬间看到结果"）
- "数据库可处理 1000 TPS"（实现细节，应使用面向用户的指标）
- "React 组件高效渲染"（框架特定）
- "Redis 缓存命中率超过 80%"（技术特定）

## 产品需求文档与功能规格（项目专属，合并自原 `product-requirement-spec` 技能）

面向本项目（法律科技）的需求分析与功能规格编写工作流，输出可落地的功能定义、验收标准与实施指引。

### 第一阶段：需求澄清

1. **背景理解**：确认需求的业务背景、用户故事与价值主张
2. **范围界定**：明确功能边界（包含/不包含），识别依赖的前置条件
3. **现有系统映射**：对照本项目现有架构分析：
   - 后端模块（workflow 节点 / agents / 路由）
   - 前端页面或组件层级（路由 / lib/queries / components）
   - 核心数据表（参考 `sqls/数据库表关系说明.md`）
4. **深度事实调研**：如需了解技术前沿（大模型 API、流式处理）、法律规范（电子证据保全标准）或竞品做法，优先调用 `deep-research` 技能输出结构化简报。

### 第二阶段：功能规格编写

每个功能规格必须包含：功能概述、用户故事、验收标准（SMART）、边界条件、前后端接口契约。

### 第三阶段：接口契约产出

制定前后端接口契约（请求/响应结构、错误码、鉴权方式），供前后端协作参考。

### 第四阶段：实施建议

输出实施步骤建议、涉及模块清单、测试要点与风险提示。

### 规范约束（验收标准 SMART）

- **S**pecific：具体明确，不含糊
- **M**easurable：可衡量（时间、百分比、数量）
- **A**chievable：可实现
- **R**elevant：与业务目标相关
- **T**ime-bound：有明确时限
