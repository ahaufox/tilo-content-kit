# Bug 运维技能 (bug-ops)

本技能提供两种工作模式：

- **模式 A：主动挖掘** — 审查近期提交，识别已逃逸审查的高危缺陷
- **模式 B：深度诊断** — 针对已报告的 bug/报错/变慢，构建反馈循环并系统性诊断到根因

---

## 模式 A：主动 Bug 挖掘

### 角色设定

你是一名深度 Bug 自动化挖掘专家，专注于识别高严重性缺陷。在开始前，先读取 `docs/00-7待办/01-当前待办/MEMORIES.md`（已上报 Bug 索引），不要重复上报已有记录的 Bug。

### 目标

审查近期提交，识别已逃逸审查的关键正确性 Bug。**仅上报**可能导致以下后果的问题：
- 数据丢失或损坏
- 系统崩溃（空指针、无限循环、资源泄漏）
- 安全漏洞（认证/授权绕过）
- 重大用户侧功能损坏

### 代码定位与结构探索规范

在执行本技能的代码查找与依赖分析时，请遵守以下优先级与防呆规则：

1. **优先使用 CodeGraph（当 `.codegraph/` 目录存在时）**：
   - **防陈旧索引**：使用前必须先在终端执行 `codegraph sync`，确保索引数据库反映最新代码变动。
   - **三大场景运用**：
     - **场景 1（跨层链路追溯）**：使用命令行 `codegraph explore "<符号名/问题>"` 批量获取源码及跨层调用关系链（Call Chain）。
     - **场景 2（全库调用点审计/影响面分析）**：使用命令行 `codegraph node <函数/类/组件名>` 检查其 callers，确保影响面审计零遗漏。
     - **场景 3（架构与符号定位）**：使用命令行 `codegraph explore "<数据结构/接口名>"` 快速定位全局符号定义。
   - **真实性校验**：通过 CodeGraph 定位到具体文件位置后，**必须使用文件查看工具读取最新真实源码内容**，严禁直接无条件盲信索引快照。

2. **降级兜底（当未建立 CodeGraph 索引时）**：
   - 使用 `grep` / `find` 或开发工具进行标准文本匹配。

### 调查策略

- **关注行为变更**：优先审查有意义的逻辑变更，忽略样式/文档改动
- **高危模式清单**：数据损坏、竞争条件导致写丢失、关键路径空指针、认证/授权绕过、无限循环、资源泄漏、静默数据截断
- **全链路追踪**：不要仅凭 diff 做模式匹配——理解调用链和下游影响
- **主动忽略**：风格问题、边缘小 case、缺乏具体触发路径的理论担忧

### 置信度门槛

- 必须能描述一个**具体的触发场景**
- 无法构造合理触发路径的，不得记入发现列表

### 输出格式

若发现 Bug，创建 `docs/00-7待办/01-当前待办/bug-<简短描述>.md`，内容包含：
- **Bug 及影响**：问题描述和用户可见影响
- **根本原因**：代码级别的根因分析
- **修复建议**：修复方式及验证建议

同时在 `docs/00-7待办/01-当前待办/MEMORIES.md` 追加一行：`<日期> | <bug-xxx.md> | <状态>`

### 重复发现防控

| 跟踪状态 | 处理动作 |
|----------|----------|
| 记录仍有效（未修复） | 不重复记录，摘要中附现有记录位置 |
| 已确认修复 | 删除记录或标记为 `fixed` |
| 已评估为不修复 | 保留记录标记为 `rejected`，除非相关代码已实质性变更否则不重新评估 |

同时删除超过 30 天的 `rejected` 记录——超期 Bug 值得重新审视。

### 禁止操作

- 禁止创建 GitHub PR
- 禁止直接修改业务代码
- 禁止创建 GitHub Issue

## 模式 B：深度诊断 (Diagnosing Bugs)

### 触发条件

当用户说"诊断"/"debug 一下"，或报告"什么坏了/抛错/失败/变慢"时使用。**除非有明确理由，不要跳阶段。**

浏览代码库时，先读 `CONTEXT.md`（如果存在）以建立相关模块的清晰心智模型，并查阅所触及区域的 ADR。

---

### 阶段 1 — 搭一个反馈循环（最重要的阶段）

**这才是本 skill 的本体。** 没有能对该 bug **变红**的紧（tight）的 pass/fail 信号，盯着代码看也救不了你。

把不成比例的努力花在这里。**要激进。要有创造性。不要轻言放弃。**

#### 构造反馈循环的方法（大致按顺序尝试）

1. **失败用例** — 在能触达该 bug 的任何 seam（单元、集成、E2E）
2. **Curl / HTTP 脚本** — 跑在 dev server 上
3. **CLI 调用** — 用固定输入，比对 stdout 与已知正确快照
4. **无头浏览器脚本**（Playwright / Puppeteer）— 驱动 UI，断言 DOM/console/network
5. **回放已抓取的 trace** — 把真实网络请求/载荷/事件日志存盘回放
6. **一次性 harness** — 拉起系统最小子集，一次函数调用触达 bug 路径
7. **Property / Fuzz 循环** — 如果 bug 是"有时输出错"，跑 1000 次随机输入
8. **差异循环** — 同样输入跑老版本 vs 新版本，diff 输出

#### 收紧循环

把循环当成一个产品来打磨：
- 能更快吗？（缓存 setup、跳过无关 init、缩小测试范围）
- 信号能更尖锐吗？（断言到具体症状，不要止步于"没崩"）
- 能更确定吗？（钉住时间、给 RNG 播种、隔离文件系统、冻结网络）

一个 30 秒的 flaky 循环几乎等于没循环；一个 2 秒的确定循环才是"紧"。

#### 阶段 1 完成标准

- [ ] **能变红** — 真的驱动到了 bug 的代码路径，断言用户描述的精确症状
- [ ] **确定** — 每次跑结果一致
- [ ] **快** — 秒级，不是分钟
- [ ] **agent 可无人值守跑**

**如果发现自己在这条命令出现之前就在读代码构造理论——停下来。** 没有"能变红的命令"，就没有第 2 阶段。

---

### 阶段 2 — 复现 + 最小化

跑这个循环。确认：
- [ ] 失败模式**正是用户描述的**（不是"旁边的另一个失败"）
- [ ] 多次跑都能复现
- [ ] 抓到了精确症状（错误消息、错误输出、慢在哪）

然后把复现样例**缩到最小、仍能变红**的场景。一次只裁一个元素，每裁一次就重跑循环。

**完成标志**：拿走任意一个元素，循环就变绿。

---

### 阶段 3 — 提假设

在动手验证之前，先生成 **3~5 个排好名的假设**。每个假设必须**可证伪**：

> 格式："如果 \<X\> 是因，那么改 \<Y\> 会让 bug 消失 / 改 \<Z\> 会让 bug 加重。"

如果说不清预测，这只是"一种感觉"——打磨锋利它，或丢掉。

**把排好名的假设列表先拿给用户看一眼，再开始验证**（如果用户不在，按排名继续）。

---

### 阶段 4 — 插桩

每个探针必须对应阶段 3 中一个具体的预测。**一次只动一个变量。**

工具偏好：
1. **Debugger / REPL 检查** — 一个断点胜过十条日志
2. **针对性日志** — 加在能区分假设的边界上
3. **永远不要"全量打日志 + grep"**

给每条调试日志加唯一前缀，比如 `[DEBUG-a4f2]`。最后清理时一次 grep 就解决。

**性能分支**：对性能回退，先建立基线测量（计时 harness、`performance.now()`、profiler），再做二分。先测量，再修。

---

### 阶段 5 — 修复 + 回归测试

**在修复之前**先写回归测试（前提是存在正确的 seam）：

1. 把最小化后的复现样例变成该 seam 上的失败测试
2. 看着它失败
3. 实施修复
4. 看着它通过
5. 拿阶段 1 的循环，在原始（未最小化）的场景上重跑

如果没有正确的 seam，这本身是一个发现——记下来，标记给架构改进。

---

### 阶段 6 — 清理 + 复盘

宣布完成之前：
- [ ] 原始复现样例不再复现（重跑阶段 1 的循环）
- [ ] 回归测试通过（或已记录"seam 缺失"）
- [ ] 所有 `[DEBUG-...]` 插桩全部删除
- [ ] 一次性原型已删掉或挪到明确标记的 debug 位置

**然后问：什么本来可以阻止这个 bug？** 如果涉及架构层改动，把球交给 `/codebase-design` skill（架构深化机会扫描章节）。
