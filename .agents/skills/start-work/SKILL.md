# 启动工作技能 (Start Work)

## 何时使用

- 每次开始新的工作会话时
- 用户说"开始工作"、"继续"、"下一步做什么"
- 从其他会话切换回来需要了解当前状态时
- 需要快速了解项目进展时

## 两种启动模式

- **轻量模式（默认，本技能主流程）**：快速读取状态、识别下一步、输出启动报告。适合日常会话启动。
- **重量模式（见文末「文档验证与计划对齐」章节）**：验证文档真实性、对齐计划、确认优先级后执行。适合新任务周期启动（合并自原 `doc-sync-planning` 技能）。

## 执行步骤

### Step 0: 前置待办审计（默认执行）

如果用户未指定具体的文件夹路径或相关动作（如"开始工作"、"继续"、"下一步做什么"），**必须先执行 `todo-management` 技能**（其模式 A 覆盖待办文档审计与归档），对 `docs/00-7待办/` 下的待办文档进行审计与归档整理，再进入后续流程。

- **跳过条件**：用户明确指定了要处理的文件夹路径、具体任务或特定功能模块，此时跳过此步骤，直接进入 Step 1。
- **调用方式**：使用 `Skill` 工具加载 `todo-audit` 技能，并按其工作流程执行。
- **目的**：确保每次启动时待办目录清晰可追溯，避免在过期或已完成的任务上浪费精力。

### Step 1: 读取项目状态

读取以下文件和目录了解当前状态（按优先级顺序）：

1. `docs/00-7待办/README.md` — 主仓待办入口与待办分流规范
2. `docs/00-7待办/04-混合/` — 主仓活跃跨仓/全栈协同专案
3. 各子仓独立待办目录：
   - `tilo-backend-app/docs/00-待办/` — 业务后端待办
   - `tilo-core-engine/docs/00-待办/` — 核心研判引擎待办
   - `frontend-v2/docs/00-待办/` — 用户前端待办
   - `admin-frontend/docs/00-待办/` — 管理后台待办
   - `prod-dev-ops/docs/00-待办/` — 运维部署待办
4. 各仓已完成归档区 `docs/00-7待办/已完成/` 及 `<subrepo>/docs/00-待办/已完成/`（查阅最近交付复盘底稿）
5. `docs/02-规划/01-蓝图与总体架构/项目总体规划与阶段路线图.md` — 阶段总体路线

### Step 2: 检查服务状态（可选）

如果用户需要运行代码，快速检查多服务拓扑状态：

```bash
# 检查业务后端是否运行 (:8110)
curl -s http://127.0.0.1:${BACKEND_PORT:-8110}/api/v1/health 2>/dev/null | head -1 || echo "Backend not running"

# 检查核心研判引擎是否运行 (:8210)
curl -s http://127.0.0.1:${CORE_ENGINE_PORT:-8210}/api/v1/health 2>/dev/null | head -1 || echo "Core engine not running"

# 检查用户前端是否运行 (:3000)
curl -s http://127.0.0.1:3000 2>/dev/null | head -1 || echo "Frontend not running"

# 检查管理后台是否运行 (:8003)
curl -s http://127.0.0.1:8003 2>/dev/null | head -1 || echo "Admin frontend not running"

# 检查联邦文档站点 Wiki 是否运行 (:8005)
curl -s http://127.0.0.1:8005 2>/dev/null | head -1 || echo "Wiki not running"
```

### Step 3: 识别下一步（决策导向）

在确定接下来的工作时，按照以下优先级进行判断和任务抽取：

1. **第一优先级：处理活跃待办专案**：优先处理主仓 `docs/00-7待办/04-混合/` 或目标子仓 `<subrepo>/docs/00-待办/` 下未完成的活跃专案（包括 P0/P1 级 Bug、当前开发阻塞或待联调项）。
2. **第二优先级：顺延处理规划需求**：当活跃专案已标记为完成并整包归档至 `已完成/` 后，才自动顺延处理 `docs/02-规划/` 目录下的 PRD 需求与重构方案。

基于以上决策路线，从读取的文档中提取：
1. **当前阶段**: 项目处于哪个阶段
2. **最高优先级任务**: 根据上述逻辑锁定的第一个核心执行任务（活跃待办优先，短期规划次之）
3. **阻塞项**: 任何已知的阻塞问题
4. **建议**: 推荐的第一个行动（基于上述优先级规则）

### Step 4: 输出启动报告

输出简洁的启动报告，格式如下：

```
## 启动报告

**当前阶段**: [阶段名称]
**最高优先级**: [P0任务描述]
**阻塞项**: [如有]
**建议**: [推荐的第一个行动]

---
准备就绪，开始工作。
```

## 核心规则

- **简洁优先**: 启动报告不超过 10 行，不要长篇大论
- **代码即真理**: 文档与代码冲突时，以代码为准
- **不执行**: 此技能只读取状态，不执行任何修改操作（todo-audit 的归档提交除外）
- **快速完成**: 整个流程应在 60 秒内完成（含前置审计）

## 输出示例

```
## 启动报告

**当前阶段**: Phase 3 — V3 驾驶舱 API 对接
**最高优先级**: 完成 cases.py 12→8 节点兼容性修复
**阻塞项**: cases.py:107 的 range(1,13) 循环与新配置不兼容
**建议**: 修复 backend/routers/api_v1/cases.py 的节点迭代逻辑

---
准备就绪，开始工作。
```

## 文档验证与计划对齐（重量模式，合并自原 `doc-sync-planning` 技能）

### 何时使用

- 每次开始**新的任务周期**（非日常会话）。
- 发现文档描述与系统实际表现存在偏差时。
- 需要向用户确认下一步最高优先级任务时。

### Step 1: 文档真实性与有效性验证

1. 深度扫描 `docs/` 下的最新文档。
2. 针对声明"已完成"的 P0/P1 模块，全量检查 `frontend-v2/src/` 和 `backend/` 下的物理文件是否存在且逻辑契合。
3. 输出真实性报告：指出文档中可能的滞后项、误报项或已过时的技术方案。

### Step 2: 目标与核心计划对齐

1. 从文档中提炼当前阶段的"北极星指标"与具体 P0 任务。
2. 将提取的计划以结构化列表呈现给用户，明确询问优先级是否需要调整。
3. 根据用户确认的结果，同步更新相关文档。

### Step 3: 启动下一步执行

1. 产出启动报告：当前坐标、服务状态、首要任务、规范红线。
2. 直接进入下一步开发任务。

### 核心规则

- **代码即真理**：文档必须服从代码事实。若两者冲突，以代码为准更新文档。
- **无确认，不执行**：P0 任务变更时，必须先获得用户明确的同意。
- **结果导向**：输出标准化 JSON 结果，包含 `status`、`message`、`data` 字段。

### 输入参数

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `validate_docs` | `boolean` | `true` | 是否执行文档真实性验证步骤 |
| `align_plan` | `boolean` | `true` | 是否执行目标对齐步骤 |
| `doc_patterns` | `array` | `["docs/**/*.md"]` | 待扫描的文档路径模式 |
