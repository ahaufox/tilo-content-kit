# 任务交接与进度同步 (task-handover)

本技能提供两个分支模式，协助团队与智能体之间进行工作进度与状态的完美传递：

- **模式 A：结构化任务交接 (Handover Mode)** — 会话结束或任务中断时，生成结构化交接记录。
- **模式 B：每日进度同步 (Daily Progress Sync Mode)** — 从真实 Git 提交逆向分析业务价值，生成标准化进度报表并注入进度文档。

---

## 模式 A：结构化任务交接

### 何时使用
- 用户要求"任务交接"、"交接一下"
- 用户要求"总结当前对话/本轮工作"、"暂存工作进度"
- 跨会话/跨智能体工作传递知识与上下文

### 工作流程

**1. 梳理当前目标**：梳理出原始需求、中途变动需求及最终达成的目标。
**2. 梳理已完成事项**：清楚说明完成了什么，修改了哪些模块/文件，解决什么问题。如果仅修改文档，注明“未涉及业务代码”。
**3. 收集修改文件**：使用 `git status` / `git diff --stat` 等列出清单（按文档、前端、后端、测试等分组）。
**4. 提炼决策与实现**：记录方案选型原因、放弃的方案及重要约束。
**5. 记录待完成/待验证/已验证事项**：
   - 待完成与待验证事项使用 checklist 格式。
   - 已验证事项需列明具体的验证动作（例如 `npm test`：通过）。
**6. 保存交接文档**：
   - 优先向当前活跃专案目录（如主仓 `docs/00-7待办/04-混合/<专案>/` 或子仓 `<subrepo>/docs/00-待办/<专案>/`）或阶段交接文档追加内容。
   - 若无，以周或阶段为单位创建新文档。禁止使用 `YYYY-MM-DD` 格式。

### 输出模板

```markdown
# 任务交接

## 1. 当前目标
-

## 2. 已完成事项
-

## 3. 修改文件清单
### 文档
-
### 前端
-
### 后端
-
### 测试 / 配置
-

## 4. 关键实现与决策
-

## 5. 待完成事项
- [ ]

## 6. 待验证事项
- [ ]

## 7. 已验证事项
-

## 8. 风险与注意事项
-

## 9. 下一步建议
1.
```

## 模式 B：每日进度同步与日报生成

### 何时使用
- 需要向项目管理或需求方同步真实的开发进度。
- 需要从真实代码库还原工作量与业务影响，并自动化撰写版本发布日志。

### 工作流程

**Step 1: 提取 Git 变更明细**
- 根据目标日期执行 `git log --since="<target_date> 00:00:00" --until="<target_date> 23:59:59" --stat` 等命令获取 commit 历史，使用 `git show` 获取具体 diff。

**Step 2: 代码与业务逻辑映射分析**
- 聚类分类（后端架构、前端交互、UI设计、ASR 核心、数据库等）
- 提炼核心功能点并推演业务影响（体现技术的硬核文件名/架构变更，以及业务层面的实际价值）。

**Step 3: 格式化表格生成**
- 将结果转换为标准化 Markdown 表格：
`| 类别 | 功能点 / 事项 | 详细描述 (业务价值与实现细节) | 状态 |`

**Step 4: 注入目标进度文档**
- 定位到指定的进度文档对应日期区域，插入或替换表格内容（按时间倒序排列）。

### 输入参数

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `target_date` | `string` | 今天 | 目标日期，格式 YYYY-MM-DD |
| `doc_path` | `string` | `沟通记录/开发进度-飞箭.md` | 目标进度文档路径 |

---

## 核心约束与执行标准

- **语言精简要求**：不要长篇大论。每个交接条目控制在 1-3 句，直接陈述事实。
- **事实依据**：进度同步的所有功能点必须在 Git 变更记录中有物理文件依据。
- **禁止项**：严禁在未经用户确认的情况下删除任何核心业务规则或文档。

## 思维链引导

在执行复杂步骤、架构设计或遇到歧义时，必须通过 `<thought>` 标签显式输出你的思考过程 and 逻辑推导，然后再输出最终行动或代码方案。
