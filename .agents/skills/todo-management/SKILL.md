# 待办与问题全景管理 (todo-management)

本技能是一个综合性的待办与问题管理工具，支持两种核心分支模式：

- **模式 A：待办文档审计与归档 (Audit Mode)** — 审计并整理 `docs/00-7待办/` 目录中的待办文件。
- **模式 B：本地/线上问题汇总 (Aggregate Mode)** — 扫描代码中的 TODO/FIXME 注释与远程 GitHub Issues 并展示汇总看板。

---

## 场景识别与分支选择

根据上下文或用户指令自动识别应走哪条分支；若无法确定，应主动提问澄清：
- 用户说 "检查待办/审计待办/归档任务/整理待办" → **进入模式 A**
- 用户说 "汇总问题/抓取 TODO/查看技术债务/汇总 Issue" → **进入模式 B**

---

## 模式 A：待办文档审计与归档 (Audit Mode)

### 何时使用
- 定期对 `docs/00-7待办/` 目录进行维护与清理
- 版本发布前确认所有计划任务的真实状态
- 对指定文件/文件夹下的 `待处理-*.md` 任务单进行归档

### 工作流程

**1. 确定审计范围**
- 若用户指明了具体文件或文件夹，则优先处理指定路径。
- 否则，默认扫描 `docs/00-7待办/` 下所有 `待处理-*.md` 文件。

**2. 任务提取与事实核对（严禁假大空完成）**
对于文档中标记为“已完成”的子任务，必须执行真实性校验：
- **代码审查**：直接调用 `code-review` 技能，通过 SSLM 四维框架与本地静态检查（ruff / mypy / lint / build）审查，看相关代码是否仍在使用 Mock/假数据，或者存在未实现的 `TODO`/`FIXME` 注释。
- **测试验证**：核查该特性是否配套了单元测试或 E2E 测试，并且测试真实执行。
- **最新交接状态**：结合近期的 `任务交接-*.md` 校验。
*只有以上三点完全吻合，才能判定为真正完成。*

**3. 模式 A 专案归档与底稿留存（强制规范）**
- **保留复盘底稿**：已完成的任务或专案，**完整移动至对应仓的 `已完成/` 目录保留复盘底稿**，严禁物理删除专案目录，未来由人工定期批量清理。
- **物理目录即状态**：物理目录位置即代表任务生命周期状态，无需维护中心化总清单或历史大杂烩汇总文档。
- **专案归档步骤**：
  - 主仓跨仓专案：`git mv "docs/00-7待办/04-混合/<专案目录>" "docs/00-7待办/已完成/<专案目录>"`
  - 子仓独立专案：`git mv "<subrepo>/docs/00-待办/<专案目录>" "<subrepo>/docs/00-待办/已完成/<专案目录>"`

**4. 处理未完成部分**
- 若文档中存在未完成的任务，调用 `task-recorder` 生成新文档 `待处理-{原主题}.md`。
- 提取并记录详细的待完成清单（编号、名称、优先级、前置依赖、验收标准）。

**5. 变更暂存**
- 操作完成后，仅将受影响的归档或待办文档使用 `git add` 加入暂存区。
- 执行提交：`git commit -m "chore(docs): 归档/整理 <主题> 待办任务"`。**严禁**一并提交无关业务代码。

## 模式 B：本地/线上问题汇总 (Aggregate Mode)

### 何时使用
- 接手新任务或切换分支时，需对齐远程与本地待办项
- 整理代码库中的 TODO/FIXME 注释以防遗忘
- 对比本地文档临时待办与 GitHub Issues 状态

### 工作流程

**1. 抓取远程 Issues (若 `local_only` 不为 `true`)**
- 执行 `gh issue list` 获取最新的 open 状态 issues（默认 30 个）。
- 若 gh 工具未安装，则平稳降级，忽略此步并输出警告。

**2. 扫描本地代码 TODOs (若 `online_only` 不为 `true`)**
- 递归扫描指定目录中的源代码文件（排除 `node_modules`、`.git`、虚拟环境等）。
- 使用正则提取含有 `TODO:` 和 `FIXME:` 的注释行、所在文件与行号。

**3. 扫描本地文档任务**
- 扫描 `.md` 结尾的文档及根目录下的 `task.md`，提取尚未勾选的任务（如 `- [ ]`）。

**4. 统一输出看板**
- 将结果汇总并输出为 Markdown 看板。

### 参数说明

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `local_only` | `boolean` | `false` | 是否只进行本地扫描（跳过 GitHub 抓取） |
| `online_only` | `boolean` | `false` | 是否只进行线上抓取（跳过本地扫描） |
| `max_issues` | `integer` | `30` | 抓取 GitHub 问题的最大条数 |
| `scan_dirs` | `array` | `["."]` | 本地扫描的根目录路径列表 |
| `exclude_patterns` | `array` | `["node_modules", "dist", ".git", "venv", "build"]` | 扫描排除的目录模式 |

## 模式 C：待办记录与归档（合并自原 `task-recorder` 技能）

当用户要求"记录待办"、"归档问题"、"整理调研结论"，或对话中发现值得记录的技术决策、架构隐患、待优化点时，将对话中的隐性知识显性化为标准化待办文档（跨会话持久化记录，不替代实时任务跟踪工具）。

### 信息收集维度

| 维度 | 说明 |
|------|------|
| 问题描述 | 用户原始输入、复现步骤、现象表现 |
| 调研路径 | 分析过程中查看了哪些文件、调用了哪些工具、排查了哪些方向 |
| 关键发现 | 根因分析、代码位置、配置差异、版本问题 |
| 涉及的代码/文件 | 完整的文件路径和关键代码片段 |
| 用户偏好 | 方案倾向性、特殊约束 |

### 文档结构与命名分类规则

生成 Markdown 文档，必须包含：`问题背景`、`分析结果`、`建议的处理方式`、`需要注意的点` 四个章节。

**按问题规模与归属分类输出**：

- **单仓日常问题/功能专案**：
  - 输出位置：当前子仓 `docs/00-待办/<NNN-主题>/` 或 `docs/00-待办/待处理-{简短主题}-{YYYY-MM-DD}.md`
  - 命名格式：`待处理-{简短主题}-{YYYY-MM-DD}.md`（主题中文、连字符分隔，禁止拼音/英文/下划线）
  - 正确示例：`待处理-documents页面流式报告生成失效-2026-05-30.md`

- **跨仓联动、全新功能设计或大型架构重构**：
  - 输出位置：主仓 `docs/00-7待办/04-混合/<NNN-主题>/`（或主仓 `01-核心研判引擎/`、`02-业务后端/`、`03-前端/` 对应分层目录）
  - 命名格式：`<NNN-主题>/` 专案目录（内部采用 Spec-Kit 三件套 `spec.md` / `plan.md` / `tasks.md` 或 PRD 结构）
  - 正确示例：`docs/00-7待办/04-混合/146-多仓文档体系与智能体协同治理重构/`

### 输入参数

| 参数名 | 类型 | 默认值 | 描述 |
| :--- | :--- | :--- | :--- |
| `title` | `string` | 自动生成 | 待办事项简短主题，用于文件名和标题 |
| `date` | `string` | 当天日期 | 待办日期，格式 YYYY-MM-DD |
| `categories` | `array` | `[]` | 额外关注维度，如 `["安全", "性能", "兼容性"]` |

### 质量检查清单

- [ ] 文件名与存放路径符合大小问题分类规范
- [ ] 包含"问题背景/分析结果/建议的处理方式/需要注意的点"四个章节
- [ ] 所有文件路径使用相对于项目根目录的路径
- [ ] 文档内容可以使用中文自然书写，禁止中英混杂的标题
- [ ] 写入成功后告知用户文件路径并请用户确认
